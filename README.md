## Estrategia de ramas
El proyecto usará **main** como rama principal, destinada a mantener una versión estable del código y la documentación.

Las nuevas funcionalidades se desarrollarán en ramas independientes siguiendo la nomenclatura **feature/nombre-funcionalidad**. Las correciones de errores se desarrollarán en ramas con prefijo **fix/**.

Cuando se finalicen los cambios, se creará un Pull Request para revisar e integrar las modificaciones en el **main**.

Esta estrategia se aplicará a medida que avance el desarrollo del proyecto.

## Convención de commits
Se utilizará una convención de commits semánticos para identificar el propósito de cada cambio:
- feat: nuevas funcionalidades
- fix: correcciones de errores
- docs: cambios en la documentación
- refactor: reorganización del código sin cambios funcionales
- test: incorporación o modificación de pruebas
- chore: tareas de mantenimiento y configuración

 Esta convención se aplicará a los nuevos commits del proyecto para facilitar la comprensión del historial de cambios.
